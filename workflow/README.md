# 工作流定义

`workflow/` 是小说生产的业务编排来源：定义要执行什么步骤、步骤依赖哪些产物、成功后产生什么、章节状态如何路由，以及模型任务使用哪些提示词、规则和契约。

`tools/` 不定义小说业务顺序。它只读取本目录的声明并负责模型调用、语义校验、重试计数、状态事务和文件读写。

```text
编排/
  流程.json                 唯一的步骤、产物、章节路由、重试策略和单元生命周期
  任务表.json               模型任务对应的 Prompt、规则包、上下文资料和输出契约
提示词/                     模型角色、任务边界和输出要求
规则/
  通用/                     通用叙事与开篇规则
  题材/                     按项目选择的题材规则包
  风格/                     按项目选择的风格规则包
  平台/                     按 project-profile 条件选择的平台规则包
  任务/                     单个模型任务的专有规则
契约/
  *.json                    模型可见的输入/输出约束与模板
  模式/                     运行产物的 JSON Schema
```

## 当前执行顺序

```text
项目设定 → 人审总纲 → 故事单元 → 章节细纲
→ 正文 → 长度/格式门槛 → 审核
→ 审核不合格：修复正文 → 再审核
→ 审核通过：提取状态 → 状态校验 → 原子提交
→ 每 3～4 章账本 → 单元评审 → 状态重建
→ 全书人工发布关卡：正式归档
```

章节步骤由 `流程.json.chapter_routes` 决定。草稿传输失败、审核格式/证据失败、状态提取失败的可重试条件和预算键由 `chapter_retry_policies` 决定；预算耗尽事件再由 `terminal_routes` 选择 `pause` 或 `fail`，不能跳到下一章。

人工对话审稿与机器自动修复分开处理：人工审稿只展示局部候选片段及后续影响，不写入任何项目文件；用户确认后默认由用户自行修改。只有用户另行明确授权代为落盘时，工具才可以修改文件。机器修复则继续按正文契约生成完整章节候选并重新校验。

`archive_run` 是全书完成后的人工发布步骤，不会在每个故事单元结束时自动执行。已提交章节需要改写时，走 `invalidate_from → 受影响细纲复验 → 重新生成`。

## 分工边界

- `流程.json`：步骤顺序、必需产物、产物输出、路由、重试策略、单元关卡。
- `任务表.json`：装配模型任务的 Prompt、规则、`context_sources` 和契约；不重复定义依赖或失败分支。
- `tools/`：执行已声明步骤，并验证“产物是否存在、Schema 是否通过、文本证据是否真实、状态是否连续、事务是否可恢复”。

例如 `config/project-profile.json` 的 `genre: "xianxia"` 和 `style: "comedy"` 分别装配修仙、喜剧规则及其运行资料；`platform: "fanqie"` 且 `channel: "male"` 才装配番茄男频规则。项目 Markdown 中出现某个词不会改变规则装配。旧运行只含 `platform/channel` 时，会按当前默认的 `xianxia/comedy` 解释，避免失去原有规则。
